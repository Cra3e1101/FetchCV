# 面经调研：默认包含牛客，小红书减少访问

## 已实施

### 2026-09-08：页面提取与本地 OCR 分离

- 正文直接读取当前帖子 ID 对应的页面状态，DOM 仅用正文叶子节点兜底，不复制整个评论面板。
- 通过浏览器调试协议读取已经完成的图片响应体，仅保存当前帖子图片列表中匹配的图片；不重新下载，不签名重放接口。同一图片的不同清晰度只保留一份，单帖最多保存 12 张已加载图片。
- 无法取得响应体时，仅截取当前可见的大图区域作为兜底；没有加载的图片不会伪装成已经保存。
- 图片写入本地后立即排队，两个 Tesseract 任务并行识别。正文采集不等待 OCR。新增 `collect_interview_ocr` 从本地队列收集结果，更新原文阅读器中的已保存、已识别数量及识别文本。
- 图片识别文字与正文分开保存，图片主导的帖子保留为 `ocr_pending`，不充当已经验证的问题。当前仍需要核对识别结果，尚未提供整组图片自动翻页加载。
- 测试脚本不再只读取两篇，不再为小红书缓存命中额外休眠两秒，优先读取未完成且业务岗位匹配的来源。

本地异步队列已通过并发/持久化测试及真实 Tesseract 中英文识别测试；本轮真实站点测试仍有未能读取的帖子，并受到原有访问预算约束，不能声称已经实现整组真实面经图片批量采集，或给出未经测量的全流程提速倍数。

只保留原有「开始面试调研／更新面试情报」入口，移除「只查牛客」「补充牛客」按钮。默认流程在本地没有相关牛客已核验来源时尝试牛客发现；小红书受限时继续牛客。来源必须真实可读，没有结果或受限时如实报告，不为满足平台覆盖而编造原帖。

小红书的共享浏览器现在使用以下策略：

- 原文入库后直接复用；搜索页面缓存 4 小时，笔记页面缓存 7 天。页面缓存与访问预算、冷却状态一起加密保存在已有本地缓存文件，重启不清零。
- 默认每 30 分钟最多 12 次导航/主动滚动，每次至少间隔 12 秒。重复 URL 的实际加载也计费；缓存命中不产生新的页面访问。每个搜索页最多额外滚动一次，每次调研最多两组站内关键词，达到预算不声称已检索耗尽。
- 同一浏览器中相同请求合并，不同岗位并发导航直接返回 busy，不堆积一长串延迟请求。
- 遇到登录、验证码、HTTP 401/403/429 或已识别的平台访问拒绝立即停止。即使已有搜索卡片也不会豁免冷却。初次冷却 30 分钟，连续失败指数增长，最长 24 小时。
- 后台研究使用独立浏览器分区，不自动导入其他浏览器或旧凭据文件中的 Cookie。用户可以在面经页点击「连接小红书」，在独立窗口手动扫码，然后点击「我已登录，继续」。登录会话由 Electron 保存在本机浏览器资料中，后续调研复用同一分区。
- 登录确认同时检查已加载页面的非访客用户状态、个人入口和会话 Cookie；仅有 `web_session` 不代表登录成功。确认过程不刷新页面、不额外调用平台接口。登录只能解除明确标记为 login 的暂停，不能清除验证码/限流冷却，也不会重置访问预算；旧版本没有记录原因的冷却同样保留。
- 小红书正文只通过共享受控浏览器读取；冷却后不再切换 HTTP、Firecrawl 等通道尝试同一来源。浏览器未配置时仅能复用已存正文并使用其他站点。
- DOM、页面现有状态和浏览器已收到的响应只用于读取已加载数据，不签名/重放私有接口。图片文字未识别时保持待 OCR，不把搜索摘要或图片猜测当作面试证据。

以上数字是 FetchCV 的保守工程预算，不是小红书公布的安全阈值，也不构成不封号保证。一次页面加载可能自带多个网络请求，滚动也可能触发网络加载。

## GitHub 调研与取舍（2026-09-07）

| 项目 | 观察 | 本项目取舍 |
| --- | --- | --- |
| [MediaCrawler 核心实现](https://github.com/NanmiCoder/MediaCrawler/blob/main/media_platform/xhs/core.py) | 分页和详情间有休眠及访问异常处理；还包含评论等采集流程 | 借鉴节奏控制与错误分类，采用更保守的共享预算；不引入评论采集或整套爬虫 |
| [xiaohongshu-mcp](https://github.com/xpzouying/xiaohongshu-mcp/blob/main/xiaohongshu/search.go) | 使用浏览器自动化，搜索读取页面状态 | 保留已有受控浏览器 DOM/状态读取；不因采用 MCP 就认为没有访问风险 |
| [RapidOCR](https://github.com/RapidAI/RapidOCR) | 支持中文、英文和离线部署，可用 ONNX Runtime | 适合作为后续本地图片 OCR；本轮没有安装模型或声称已运行 OCR |
| [PaddleOCR](https://github.com/PaddlePaddle/PaddleOCR) | 图片/文档文字识别工具链 | 更复杂的图片文档处理可评估使用；不是降低网站访问频率的替代品 |

结论：优先减少访问并复用结果，比换一种提取文本的方法更直接。截图 OCR 用于解决图片正文，控制台/DOM 提取用于解决已渲染文本；二者都不能消除加载页面或翻页时的平台风控。

## 验证范围

使用模拟时钟、模拟页面和隔离浏览器入口测试验证冷却、预算持久化、请求合并、默认多平台调研，以及后端证据流程。手动登录恢复测试验证登录不清除限流和预算。没有使用真实小红书账号做高频或风控压力测试。

### 2026-09-08 图片修复验证

已使用用户授权的登录会话读取真实帖子正文。之前部分详情失败的原因是搜索访问链接被推荐/个人主页链接挤出缓存；已限制缓存对象并保留搜索链接，回归测试覆盖缓存淘汰和恢复。

图片优先复用浏览器已收到的响应内容，再以当前可见图片截图兜底，交给两个本地 Tesseract 工作进程处理；浏览器不等待全部 OCR 完成。原文和 OCR 分开保存，待核验 OCR 不作为已证实面试题。

隐藏窗口可能先发出空的 paint 帧。现在仅保存非空帧，截图等待有效绘制事件，最长 2 秒，不为每篇帖子固定增加延迟。页面提取缓存版本更新为 4，避免复用旧的截图失败状态。

`scripts/test-image-preparation.mjs` 无网站请求验证截图、已加载图片两条路径，均实际调用本机 Tesseract 并断言识别到 SQL。`scripts/test-xhs-image-live.mjs` 仅抽测一篇已知帖子，使用原登录资料和共享预算。此次真实抽测被本地 30 分钟访问额度阻止，没有发出帖子请求，因此尚不能确认真实小红书图片批量识别成功。
