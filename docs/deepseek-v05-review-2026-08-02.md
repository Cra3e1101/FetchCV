# DeepSeek v0.5 建议复核与 v0.4.18 落地记录

本记录复核用户提供的《FetchCV 第四轮多角色闭环优化方案》。裁决原则是：保留单一 Pi Agent Loop 与 ToolGateway，不以一次大迁移替代可验证的小步演进。

## 本轮直接采用

- 前端运行状态显式化：区分连接模型、流式回答、真实工具执行、等待审批、暂停、失败与就绪。
- 流式消息批量刷新：模型 delta 先进入岗位级缓冲区，再按动画帧合并到 React 状态。
- 外观设置持久化：主题色、密度、浅色 / 深色 / 跟随系统统一写入本地设置 JSON，并在应用启动时恢复。
- Token 收敛：删除重复的颜色 `:root`，保留单一有效色彩源；新增语义 surface / text token。
- 动效纪律：状态变化使用短时过渡，继续尊重 `prefers-reduced-motion`；不显示隐藏思维链、虚假百分比或预计剩余时间。

## 改造后采用

- “状态机”采用纯函数映射现有 Pi / Task / Approval 事件，不在前端创建第二份业务状态机。
- 暗色模式延续 FetchCV 暖灰与低饱和强调色，不机械反色；PDF / Word 文档保持自身排版。
- 性能治理先解决逐 token 重绘。消息虚拟化只有在 200 条真实消息基准仍不达标时引入，避免现在增加滚动锚点和动态高度复杂度。
- 大组件拆分继续进行，但不在同一版本同时引入 Zustand 并改写全部数据流；状态所有权需先按岗位、任务、设置边界稳定下来。

## 暂缓

- 预计剩余时间：模型与网页工具耗时不可稳定预测，展示会制造错误预期。
- 一次性加入 Tracker、批量岗位、结构化澄清、Trace Inspector、行为偏好和审批撤销：这些都值得做，但需要分别定义持久化模型、权限与验收，不能作为视觉重构的附带改动。
- 全量消息虚拟化与 TypeScript 迁移：作为性能基准或接口事故驱动的工程里程碑，而非版本数字驱动的重写。

## 下一批优先级

1. 面向用户的 Trace 搜索、筛选与脱敏导出。
2. 结构化岗位理解纠正卡，而不是额外聊天轮次。
3. 审批 append-only 历史、撤销与版本回滚的完整事件化。
4. 投递生命周期追踪，但不自动投递。
5. 用真实性能基准决定是否引入虚拟列表。
