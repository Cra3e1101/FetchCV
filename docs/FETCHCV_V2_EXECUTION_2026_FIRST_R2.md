## 1. 本次更正：更新依据，也改变实施重点

上一版引用了较多 2021–2025 年的 RAG/长上下文研究，对当前 Agent 运行机制的覆盖不足。按用户要求调整如下：

- Agent/记忆/上下文/检索研究优先选择 **2026-01-01 至 2026-09-21 首次公开的工作**。2026 正式发表但 2025 已有预印本的研究另列，不能包装成 2026 才出现的算法。
- 工程实践以 **2026 活跃版本的源码与变更记录** 为准。项目创立时间早，不代表当前实现旧；但旧版教程、退休分支和不同语言 SDK 的说明不能混用。
- 不再以 BEIR、MIRACL、ALCE、Lost in the Middle、LongMemEval 2025、Sufficient Context 2025、HippoRAG 2 作为本版 Agent 算法的主要决策依据。已有引用验证、FTS 基线等合同保留，因为它们本身是产品要求，不需要为了年份换掉可靠基础。
- 基础存储、文档和恢复只参考近两年的现行成熟实现；前沿实验的成熟度单独标注。只更换参考资料、不改变工程决策，不算优化。

**主要变化：SDK 能力复用优先；轻量 Agent 运行层；检索结果按需读取；跨会话行动评测；可回溯的过程经验；预算内自适应检索；分阶段上下文管理。**

## 4. Agent 运行层：减少默认机制，明确执行边界

### 4.1 单 loop 与按需能力

保持单 Pi loop。对简单问题不加规划模型、长期记忆提取、反思、自我评审或多代理。可用工具按当前任务和授权 scope 提供，skills 先传简短索引，明确命中才读取正文。复杂任务需要计划时再启用计划状态，不要求每个回复都先写 Todo。

这参考 F2 的现行产品取舍，但不把其基准收益直接套用到 FetchCV。需测首 token、请求输入 token、工具选错率与任务成功，而非只报告提示词缩短了多少。

### 4.2 薄的模型能力配置

用版本化 `ModelProfile` 描述 context/output 上限、工具与结构化输出能力、图像输入、token 估计器与请求适配；默认一个简单通用 profile，只为已验证差异增加覆盖项。Profile 无权改变用户批准、scope、秘密发送策略或允许的外部写动作。

记录 provider/model revision、profile revision、工具 schema hash。模型窗口未知时保守处理并报告，不能拿最大窗口兜底。未来更换模型首先跑同一合同和领域评测，不重写业务逻辑。

### 4.3 checkpoint 与副作用

APP 保存可恢复的运行状态、最后确认的事件序号、工具执行记录与未完成工作；展示用摘要是可再生视图。恢复时重新核验授权、目标版本和工具 schema，不能仅凭摘要里的“已批准”自动继续写入。

本地写+receipt 原子提交；外部请求结果不明保持 unknown，不自动重发。使用 F3 的职责区分，继续沿用原方案的单写者/CAS/幂等合同。无需引入 LangGraph 运行第二个模型循环。

## 5. 上下文管理：先按需读取，再考虑复杂压缩

### 5.1 大工具结果改成“短摘要 + 不透明引用”

网页正文、长 PDF 文本、检索批次和执行日志可存入宿主管理的内容对象；模型收到状态、摘要、大小和 `result_ref`，通过受限 read/search 工具取所需片段。`result_ref` 绑定 workspace、run/tool call、内容 hash 与权限；不能直接是任意本机路径，读取时重新检查撤权/tombstone。

唯一性不能只依赖可空 tool-call ID，采用宿主生成 ID 并验证无碰撞；磁盘满、保存失败、对象不存在、引用跨 scope 都应显式失败。不要在文件未保存时告诉模型“已存”。这是从 F2 的 offload 机制/近期修复得到的设计要求，尚未在 FetchCV 实现。

### 5.2 分层压缩与提交屏障

按顺序比较：

1. 基础合法消息组装，保留原文；超长输出使用引用与定向读取。
2. 对已完成的历史工具组做确定性精简，保留参数/结果状态/receipt/来源引用；不删权威记录。
3. 有需要再对选定历史片段作摘要；保留最新用户输入、当前未闭合工具组、关键约束和可回读来源。
4. 仅在前述方案仍失败时比较 AgentFold 风格的多尺度选择。它的训练与协议成本单独评估。

压缩采用单次在途机制及 revision 检查：准备候选上下文 → 验证预算/引用/工具组 → 在安全回合边界原子切换。用户新输入、cancel 或 schema 变化使候选过期时不提交；压缩失败不能吞掉 steering/follow-up 队列。恢复次数与额外模型调用有上限，失败即返回可解释状态，不无限 compact/retry。

首次轻量引用/预算保护在 M3 交付；高级摘要在 M8。若 M3 没有合适的安全切换接点，先只做发送视图转换，保留 checkpoint，不急着修改 SDK 内部循环。

### 5.3 缓存与质量共同验收

稳定 policy/tool schema 区与每次任务/证据分开组装，减少无意义变动；provider 支持缓存时报告实际 cached tokens、总成本、首 token 和冷/热延迟。不能为缓存而保留已撤权信息。压缩率本身不是目标，关键是恢复后还能遵守约束、正确用证据并完成任务。

## 6. 检索：显式约束、精确查找、语义检索、证据校验

保留 FTS 独立可用。按本轮读取的 N1 思路，将三种检索信号明确区分：词法匹配、可选 dense、结构化实体/时间/版本条件。授权过滤由宿主计算，模型只能在已授权集合内提出条件，不得扩大 scope。

建议最小分流：

| 问题类型 | 优先路径 | 升级条件 |
|---|---|---|
| 明确简历/岗位/来源 ID | 直接按对象与版本读取 | ID 不存在/歧义时明确处理，不用语义相似替代身份 |
| 公司名、岗位编号、精确措辞 | FTS + metadata | 必要证据未覆盖时补充语义检索 |
| 同义表达、经历匹配 | FTS+dense 候选融合 | 经 tune/validation 证明优于纯 FTS 才默认推荐 |
| 跨来源/时间变化/多跳 | 查询拆分、分步补证据 | 限工具次数/token/时限；不默认开启无界 deep search |

RRF 仍是可解释候选融合方式，不被包装为 2026 新算法；SimpleMem 论文的集合合并也不能误说成 RRF。固定 top60 作为对照，自适应深度必须受硬上限约束，比较同预算质量/成本。

用 N4 的诊断方向更新评测：

- 没找到足够证据：改检索/解析/覆盖。
- 已找到足够证据却回答错：改证据选择/理解/生成，不能一律继续检索。
- 缺证据仍强答：改拒答与澄清策略。

保留原文合法定位、引用语义支持、断言覆盖、数字/日期一致性作为产品硬要求。source_text、index_text、prompt_text 的分层不变。新研究只改变如何寻找和用证据，不让摘要或相似向量成为履历事实。

## 7. 记忆：加入过程经验，但不让经验成为权限

原方案已有事实与记忆分离，本版进一步明确四种内容的读写行为；首版优先用既有实体和版本化 payload 表达，不为了概念分类先新增四套数据库。

| 内容 | 权威依据 | 写入/启用方式 | 失效依据 |
|---|---|---|---|
| 个人事实、偏好、约束 | 原资料/用户确认 | 保留 pending/confirm/active 与原权限 | 撤回、矛盾、有效期、来源撤权 |
| 任务经历 | 真实操作、观察、receipt、结果 | APP 记录事实性事件，不存秘密和隐式思维链 | 保留策略、scope、版本 |
| 过程经验 | 可追溯的任务成功/失败记录 | 生成候选并验证适用条件；涉及长期个人记忆仍遵守用户确认 | 工具 schema、平台、环境、证据版本变化 |
| 工作摘要/索引辅助 | 原消息、资料和事件 | 可再生缓存，不能自动升级为 active 事实 | 原文变更/撤权、摘要 revision |

过程经验的建议字段：`scope, task_type, preconditions, tool_schema_hash, environment_revision, observed_outcome, evidence_refs, limitations, status`。例如“这个导出流程需要先选择当前简历版本”可成为候选；“用户上次批准了投递”不能转成下次自动投递许可。失败经验要分清暂时网络/磁盘问题与稳定行为，避免永久记住一次偶然错误。

先用 N1 的实体/时间/原子候选方法，但原始引文保留，指代/相对日期无法确认时记为 unknown，不由模型补造。其“semantic lossless”命名不构成无损保证。N2 支持将原始轨迹片段、状态变化与流程提示区分检索；N6 多粒度算法后置，不改变确认与权限。

查询时先读小 manifest，再取必要原始证据；不默认把全部历史交给另一个 coding agent。N2 的高准确率配置有明显查询成本，尚不满足 FetchCV 本地即时查询要求。

## 8. 评测改成“会做后续任务”，而非只有历史问答

原 §21 的 60 份资料/400 query/100 对话序列和安全、引用、召回、包体、启动门槛保留。旧论文不作为这些门槛的前沿论据；它们是项目自身冻结的目标。

增加一个最小的 **12 条、每条至少 3 会话的合成任务链 pilot**，只用于发现实现缺陷，不用 12 条成绩宣称生产质量。分四组，每组三条：

1. 用户先给地点/岗位约束，后续筛选不得丢失约束；再修改约束，应停止使用旧偏好。
2. 导入经历→改简历→按新 JD 生成内容，区分事实、建议与未经确认的能力。
3. 生成草稿→取消或进程退出→恢复，能读回状态，但不自动重复提交。
4. 来源更新/撤回或工具 schema 改变后，旧经验失效；错误前提需指出，不能生搬流程。

这是受 N2/N3 启发的 **FetchCV 自建任务**，不是官方 benchmark 成绩。正式规模及 sealed 分配在 pilot 发现任务定义问题后冻结；原有集合不被这 12 条替代。

| 对照实验 | 固定条件 | 评价重点 |
|---|---|---|
| 当前合法 assembly vs 引用读取 vs 历史组精简 vs 选择性摘要 | 同任务/模型/总预算 | 成功率、约束遗忘、无据事实、额外 read 次数、token/延迟 |
| 固定检索深度 vs 有界意图分流 | 同 scope/语料/模型/预算 | 必要证据覆盖、知识利用、拒答、召回/nDCG、成本 |
| 无长期记忆 vs 事实记忆 vs 事实+过程经验 | 同任务链、会话重置规则 | 后续任务成功、过时经验误用、重复外部操作、source 撤权 |
| 单粒度 vs 原文/摘要/过程多粒度 | 同生成器/上下文 token | 净质量收益、源定位、确认精度、构建与查询成本 |

按 source 家族/任务链切分，计算配对差值与区间；固定 reader/生成模型、judge 与 prompt revision。测试中故意提供误导/缺失/被撤回证据。记录实际工具和副作用，不把模型宣称“已完成”当结果。sealed 结果用于调整后，它就是已知回归集，下一次泛化声明需新 sealed。
