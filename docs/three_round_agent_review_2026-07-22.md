# FetchCV 三轮 Agent 架构与产品审查（2026-07-22）

本审查以 `0.4.1` 代码、`test use/高子强的简历.pdf`、`test use/JD.txt` 和 Windows 客户端为基线，三轮架构落地版本为 `0.4.2`；面试调研输出边界与轨迹聚合修复发布为 `0.4.3`。结论不是角色扮演式意见清单；每轮都经过“架构师 → 产品经理 → 三类用户 → 产品复核 → 实现与测试”的闭环。

## 外部研究基线

| 来源 | 借鉴 | FetchCV 的取舍 |
|---|---|---|
| Pi / oh-my-pi | 极简模型循环、原生工具调用、会话与 steering | Pi 只负责模型回合；权限、审批、版本和审计继续由 ToolGateway 负责 |
| LangGraph / OpenAI Agents SDK | 可序列化运行状态、中断与恢复 | 为 Electron Pi 任务增加持久检查点和宿主锁恢复，不引入第二套图编排 |
| OpenHands SDK | Agent 生命周期、沙箱、模型无关边界 | 保留 provider-independent runtime 和受控工作区，不开放任意 Shell |
| Pydantic AI | 类型化工具、可观测性、基于结果的评估 | 继续用 Pydantic 输入输出与 Trace；运行证据不使用模型自评分 |
| Context-mode / MemGPT | 分层上下文、持久记忆、按需载入 | 固定事实与审批优先于最近对话和旧摘要；网页与工具输出标记为不可信数据 |
| ReAct | 推理、行动、观察交替 | UI 展示可验证行动摘要，不暴露或伪造隐藏思维链 |
| Reflexion | 从外部反馈中学习后再试 | 只记录真实工具失败、用户引用纠正和审批，不保存模型自我评价 |
| WebArena | 以环境结果而非文本相似度验收 | 用真实 PDF/JD、版本血缘、审批、PDF 产物和工具记录验收 |
| Human-AI Interaction Guidelines | 预期管理、纠错、可控性 | 当前动作优先、完整轨迹按需展开、关键副作用逐次确认 |

## 第 1 轮：可靠 Agent，而不是一次性模型调用

### 三类用户压力测试

1. **隐私敏感的数据分析求职者**：最怕改写夸大事实，且不接受客户端崩溃后重复写文件。
2. **有成熟作品集的 AI 产品求职者**：长任务会边做边补充，希望中断后继续而不是重新分析全部材料。
3. **管理二十个岗位的高级用户**：会切换模型、暂停任务和重启应用，要求运行状态可恢复且副作用幂等。

### 产品复核

原架构的正确部分是 `Pi AgentHarness → ToolGateway → 领域状态`；问题在于 Pi session 仍是进程内对象。后端虽然保存任务和业务状态，Electron 异常退出后旧任务锁可能残留，实时推理轨迹也无法复原。

### 已实现

- 每个 Electron 进程拥有独立 `host_id`；新宿主可识别并释放旧宿主留下的孤儿任务。
- Pi 任务在模型回合、工具观察和回答阶段持续写入有序检查点。
- 检查点保存回合号、阶段、部分回答和最近 40 条真实处理事件；敏感文本经 Trace 脱敏。
- 恢复任务只把检查点当作线索，仍要求先读取持久工作区验证，避免重复副作用。

## 第 2 轮：上下文、证据与可验证学习

### 三类用户压力测试

1. 数据分析用户要求 JD 引文和简历事实永远压过聊天里的随口描述。
2. AI 产品用户要求看到 Agent 到底读取了什么，而不是一句“我已分析”。
3. 高级用户故意让网页读取失败后重试，检查 Agent 是否重复相同失败动作。

### 产品复核

旧上下文压缩按字符截断，能控制长度，但没有明确优先级；历史摘要还曾以合成用户消息注入，容易与新指令混淆。工具轨迹存在于后台，回答界面却缺少面向用户的收据。

### 已实现

- 上下文优先级固定为：目标与已验证事实 → 用户明确审批/纠正 → 当前阶段与最近回合 → 工具证据 → 旧摘要。
- 历史摘要移入受标记的系统记忆块，不再伪装成用户消息；网页、附件和工具输出明确为不可信数据。
- 只把真实失败的工具步骤写入 operational memory，并要求副作用重试前检查持久状态。
- 每个助手回答可附结构化工具收据：工具数、证据数、结果摘要、是否等待确认。
- 右栏运行证据增加“长任务可恢复检查点”，继续使用确定性证据而非 AI 分数。

## 第 3 轮：渐进透明与桌面交互

### 三类用户压力测试

1. 新用户只想知道当前在做什么，不愿阅读十几步内部日志。
2. 熟悉 Agent 的用户要求随时展开完整工具过程，并能引用回答继续追问。
3. 小屏和缩放用户要求新事件平滑上推、输入框始终在底部、任务完成后自动收起。

### 产品复核

完全隐藏过程会失去信任，完全展开又会挤压对话。正确策略是 context-sensitive progressive disclosure，而不是固定列表或假思维链。

### 已实现

- 运行中默认展示最近五步并持续突出唯一当前动作；此前步骤可一键展开。
- 新事件使用布局动画平滑进入，当前文字使用克制的横向流动高光；系统减少动态效果时自动关闭动画。
- 完成后处理区自动折叠，回答下方保留可追溯工具收据。
- 输入框仍是布局底部的真实行，不以 fixed/absolute 覆盖消息；Enter 发送、Shift+Enter 换行、选择回答后引用均保留。

## 最终架构边界

```text
Pi AgentHarness
  ├─ provider adapter / streaming / steering
  ├─ context transform / native tool calls
  └─ durable checkpoint heartbeat
          ↓
FetchCV ToolGateway
  ├─ typed schemas / stage scope / permission
  ├─ approval / idempotency / version / trace
  └─ web / workspace / resume / interview / Skill / MCP
          ↓
SQLite domain state + PDF/editor artifacts
```

FetchCV 不采用“让模型直接拥有所有能力”的方案：Pi 官方边界不包含权限系统，招聘材料又包含个人信息和本地文件副作用。让模型负责语义判断、让 ToolGateway 负责真实世界约束，是当前业务下更小且更可靠的组合。

- ESLint：通过。
- Pi Harness：3 项通过。
- Pi bridge + Agent platform：15 项通过，1 项按环境跳过。
- 真实材料：PDF/JD 连续性 2 项通过，JD 导入 2 项通过。
