# FetchCV 产品需求文档

> 产品：FetchCV
> 形态：本地优先的桌面求职 Agent
> 产品版本：0.4.19 Alpha
> PRD 版本：V4.2
> 更新日期：2026-08-02
> 基线：仓库中的 `windows/` 源码目录

## 1. 产品定义

### 1.1 一句话定位

FetchCV 在用户现有简历和真实经历基础上，围绕目标岗位完成材料理解、岗位调研、证据化改写、简历编辑导出、面试情报和版本追踪。

### 1.2 核心问题

求职者通常已经拥有较成熟的简历，但面对不同岗位时仍需要：

1. 从分散材料中建立可信的个人经历库。
2. 理解 JD 背后的岗位目标，而不是只抽关键词。
3. 在不编造事实的前提下重新组织同一段经历的表达重点。
4. 保留原简历结构和排版，并得到可编辑、可核验的新版本。
5. 基于真实面经准备面试，而不是依赖模型凭空猜题。
6. 清楚知道 Agent 读取了什么、调用了什么、修改了什么。

### 1.3 产品不是

FetchCV 不是：

- API 套壳聊天框；
- 关键词触发的固定工作流；
- 把选中经历机械拼进 PDF 的生成器；
- 编造数字、职责或技能的简历写手；
- 用不透明百分比冒充 ATS 通过率的评分器；
- 未经确认自动投递、发邮件或操作外部账户的机器人；
- 展示隐藏思维链或伪造“思考过程”的演示界面；
- Claude、Codex 或其他产品的品牌换皮。

## 2. 产品原则

### 2.1 先建立资料，再处理岗位

```text
导入基础简历和补充材料
→ 核对并建立个人资料库
→ 创建岗位项目并导入 JD
→ Agent 解释岗位理解
→ 讨论经历与表达策略
→ 审批改写
→ 编辑、预览与导出
→ 面试调研
→ 用户实际投递后记录版本
```

不得要求用户在导入简历前先锁定事实或创建岗位。

### 2.2 保留成熟简历的连续性

- 个人信息、教育等稳定内容默认保留。
- Agent 优先修改措辞、排序和强调重点，不随意重建整份简历。
- 同一段产品经历可以在数据分析岗位中突出数据工作，也可以在产品岗位中突出需求、方案和协作，但事实强度不得变化。
- 基础简历永不被岗位改写覆盖。

### 2.3 模型负责判断，代码负责约束

模型负责：

- 理解用户意图和 JD；
- 选择是否调用工具；
- 制定岗位策略；
- 生成有证据的改写建议；
- 综合面经并提出准备建议。

确定性代码负责：

- 权限、审批和作用域；
- 状态与任务生命周期；
- 数据库事务和版本；
- 事实来源、数字、日期和角色强度校验；
- 文件路径与网络边界；
- 副作用幂等和未知结果处理；
- PDF / DOCX 渲染与保存；
- 脱敏、审计和错误恢复。

### 2.4 单一 Agent Loop

桌面端只允许一个 Pi Agent Loop 负责模型决策。Python Sidecar 不得运行第二套模型 Agent。

```text
User / UI
→ Pi model loop
→ structured tool request
→ ToolGateway
→ deterministic domain tool
→ persisted result
→ next model turn
```

普通聊天、岗位优化和面试调研共享同一运行模型，但使用不同的上下文和工具集合。

### 2.5 通用能力不硬编码场景

天气、新闻、公司动态等实时问题由模型根据语义调用通用网页搜索和网页读取工具，不在生产工具集中注册 `get_weather` 一类固定业务工具，也不通过关键词表决定是否联网。

业务专用工具只用于存在稳定领域数据结构和约束的能力，例如读取岗位上下文、生成简历提案、写入岗位版本和构建面试简报。

### 2.6 透明但不泄露隐藏推理

界面可以展示：

- 当前正在执行的动作；
- 已完成步骤的简短摘要；
- 工具名称、输入范围、状态和结果；
- 证据来源、错误和下一步；
- 运行耗时和可折叠历史。

界面不得展示：

- 模型隐藏思维链；
- 长篇工具抓取正文；
- DSML / tool-call 协议原文；
- API Key、Cookie、Token 和本地隐私路径；
- 与当前任务无关的模板化“理解问题 / 准备上下文”列表。

## 3. 信息架构

### 3.1 左栏：资料与岗位

- 个人资料库；
- 基础简历与经历；
- 作品、网站、仓库、证书等材料；
- 按公司折叠的岗位项目；
- 用户入口与设置。

### 3.2 中栏：持续工作区

- 对话；
- 简历；
- 面试；
- 当前动作和可折叠执行记录；
- 阶段内的结构化审批组件；
- 始终固定在底部且不遮挡消息的输入框。

### 3.3 右栏：上下文与证据

右栏不重复聊天内容，负责展示：

- 当前任务状态；
- 岗位要求覆盖和证据；
- 简历版本与事实来源；
- 未决审批和未知副作用；
- 面试来源、共性问题与证据充分度；
- 下一步建议。

窗口变窄时右栏可折叠，但关键阻塞状态必须在中栏保留入口。

## 4. 端到端需求

### 4.1 首次使用与简历导入

流程：

```text
选择 PDF
→ 本地解析
→ 可选脱敏 AI 增强
→ 展示原始文本与结构化预览
→ 用户修正、排序或删除
→ 确认入库
```

验收要求：

 - AI 增强默认关闭；即使用户选择增强，也必须先完成本地解析并展示实际脱敏外发文本，用户再次确认后才能调用模型。
- 不上传 PDF 二进制、本地路径、姓名、联系方式、证件号和详细地址。
- 模型失败时回退本地解析，不阻断导入。
- 用户可修正模块、标题、组织、角色、起止日期和正文。
- 入库内容必须来自用户确认后的同一份预览快照。
- 重复文件必须识别，不得重复创建全部经历。
- 预览停止后不得写入半成品资料。

### 4.2 岗位创建与 JD 导入

支持：

- 手动粘贴；
- TXT / Markdown 导入；
- 多岗位文本拆分后选择；
- 公开招聘网页读取；
- 公司、岗位名和 JD 后续编辑与删除。

要求：

- 网页读取失败时说明原因，不用猜测内容补齐。
- 已有 JD 被覆盖前必须确认。
- 删除岗位不得删除个人资料库。
- 每个岗位的数据、对话、任务和版本完全隔离。

### 4.3 岗位理解

Agent 必须向用户说明：

- 岗位目标和核心职责；
- 硬要求、加分项和风险点；
- JD 中的原始证据；
- 当前资料能支持什么、缺少什么；
- 建议的简历表达主线。

Agent 不得分析完成后直接跳到经历选择，也不得把本地规则结果伪装成模型判断。

### 4.4 经历策略与简历改写

要求：

- 以完整经历为单位组织，不拆散学校、时间、专业、GPA 和奖项上下文。
- 说明每段经历在当前岗位中承担的能力证据。
- 只调整有来源的表达，不增加不存在的项目、数字、工具或职责。
- 每条提案显示原文、建议文本、JD 依据、事实依据和风险。
- 用户可采用、保留原文或编辑后采用。
- 审批草稿在提交失败或关闭页面后仍可恢复。
- 只有后端确认提交成功后才清除草稿。

### 4.5 岗位要求覆盖

不得使用“ATS 通过率”。

每条要求使用：

- `支持`：存在可定位的直接证据；
- `部分支持`：存在相关证据，但范围或强度不足；
- `暂无证据`：当前资料中没有可定位证据。

每项必须展示 JD 原文和简历/事实证据。矩阵可展开全部要求，不能只显示前几项。

### 4.6 简历编辑、预览与导出

- 基础版和岗位版必须明确区分。
- 编辑器、预览和 PDF 使用同一编辑器快照。
- 预览区只显示当前已生成版本，不使用默认示例简历。
- 用户可直接编辑内容、模块、顺序和排版。
- PDF 保留正式模板版式。
- Word 是独立的单栏可编辑 ATS 版本，不替代 PDF。
- 保存失败时保留本地编辑状态并允许重试。

### 4.7 面试情报

流程：

```text
读取公司、事业部、岗位和 JD
→ 检索本地知识库
→ 发现公开面经
→ 读取原文并保存证据
→ 提取真实问题
→ 聚类共性问题
→ 结合用户经历给出准备建议
```

要求：

- 优先检索同公司、同业务线、同岗位；不足时扩展到同公司同类岗位和未注明事业部的相同岗位。
- 小红书来源按发布日期倒序，展示时间、原始链接和本地证据副本。
- 链接失效时明确标记，不以本地副本冒充原始链接。
- 无账号公开访问优先，不导入用户 Cookie，不自动扫码或绕过验证码。
- 设置访问预算、缓存、间隔与熔断，降低触发封禁风险。
- 小红书证据不足后再使用牛客、知乎等补充来源，并清楚标注平台。
- 共性问题必须能展开查看来源摘要、出现次数和准备建议。
- 抓取过程和长正文不占据主对话；详细证据进入右栏。

### 4.8 普通对话与网页工具

- 所有普通问题都通过已选择模型处理。
- 模型可根据语义选择搜索网页、读取网页、读取附件或本地工作区。
- 不以关键词表决定工具调用。
- 动态网页在 Agent 内受控读取，不无故打开外部窗口。
- 搜索回答必须保留可点击来源。
- 工具失败时说明已尝试什么和下一步，不能输出空回答。

## 5. Agent Runtime

### 5.1 任务状态

最小状态：

```text
queued
running
paused
awaiting_approval
blocked
completed
failed
cancelled
```

- `cancelled` 是终态，只能创建新任务，不能伪装成“从中断处继续”。
- 重启时对旧 Host 的 `running` 任务进行 reconciliation。
- 存在未知副作用时任务进入 `blocked`，不得自动继续。
- 前端必须把模型连接、流式回答、工具执行、等待审批、暂停和失败映射为不同可见状态；不得只用单一 `busy` 布尔值生成含糊文案。

### 5.2 消息与岗位隔离

- busy、Activity、错误、AbortController 和排队消息按岗位隔离。
- 切换岗位不能让旧响应覆盖当前工作区。
- 停止当前岗位任务不能中止其他岗位。
- 运行中切换默认模型不影响任务绑定的 Provider/model 快照。

### 5.3 上下文

必须固定保留：

- 完整 JD；
- 基础与岗位简历结构；
- 已验证事实和来源；
- 用户纠正和审批决定；
- 当前任务模型快照；
- 关键工具结果与产物引用。

旧对话可压缩，但不能只依赖消息截断。网页内容和工具输出均视为不可信数据，不能修改系统策略。

### 5.4 副作用

- 所有写操作使用稳定 `operation_id`。
- 状态至少包括 `prepared → running → completed`。
- 已知失败可按策略重试；写操作不得自动重复执行。
- 未收到明确回执时标记 `outcome_unknown`。
- 用户必须看到工具、来源、目标、时间、最后状态和每种处理决定的后果。

## 6. ToolGateway、权限与扩展

### 6.1 权限模式

工具权限至少支持：

- 允许；
- 每次询问；
- 拒绝。

读取和写入分开配置。关键写操作必须在真实执行前审批。

### 6.2 Skill

- 只从受控根目录加载。
- 新发现 Skill 默认关闭。
- 授权绑定内容哈希。
- 文件变化后自动停用并要求重新审查。
- Skill 只能提供工作流与判断规则，不能绕过 ToolGateway。

### 6.3 MCP

- 支持 stdio 和受控 HTTP 连接。
- URL 不得包含凭据型 Query。
- Server 自报 `readOnlyHint` 仅是声明，不是授权。
- 每个只读工具逐项允许。
- 写工具需要工具、目标和运行审批。
- Schema 或能力注解变化后清除旧白名单。

### 6.4 本地文件

- 用户可导入任意文件到隔离工作区。
- Agent 可列出、读取和搜索允许范围内的文件。
- 删除、移动、覆盖和外发文件必须询问。
- 当前不提供任意 Shell。

## 7. 模型与隐私

- 支持 OpenAI-compatible 与 Anthropic-compatible Provider。
- 模型和推理程度从输入框内统一入口选择。
- Key 使用 Electron `safeStorage` / DPAPI。
- Key 不进入任务、数据库、Trace 或前端状态。
- 出站数据递归处理身份信息、联系方式、证件号、地址、路径、Authorization、Cookie、Token、API Key、私钥和 URL Secret。
- AI 增强和外部网页访问必须向用户说明真实外发范围。
- Sidecar 只监听 loopback，并使用控制令牌。

## 8. 交互与视觉

- 视觉基调：Claude 风格的克制、温和和高信息密度，不使用通用 AI Dashboard 卡片堆叠。
- 默认正文不得小于桌面可读基线；右栏和来源列表不得用过小字号压缩信息。
- 输入框永远位于对话布局底部，不覆盖消息；窗口缩放后跟随容器变化。
- Enter 发送，Shift+Enter 换行；中文输入法合成期间不得误发送。
- 新执行事件平滑进入并推动旧内容上移；完成后自动折叠为一行摘要。
- 当前动作可使用从左到右的轻微文字流动，必须支持 `prefers-reduced-motion`。
- 长工具过程自动归并，例如“读取 8 篇面经”，不重复显示 8 个同名条目。
- 用户选中 Agent 回答后可引用到输入框。
- 设置弹窗点击遮罩或 Escape 可关闭；忙碌中的不可逆操作除外。
- 支持浅色、深色和跟随系统；选择持久化到本地 JSON，并在进入工作区前应用。
- 主题色、明暗模式和密度来自同一外观配置；正式简历文档不随桌面暗色模式反色。
- 流式回答按浏览器动画帧合并渲染，不能为每个 token 重绘完整消息树。

## 9. 成功指标

### 9.1 产品指标

- 首份基础简历成功入库率；
- 岗位理解后的用户纠正率；
- 改写建议采用 / 编辑 / 拒绝分布；
- 从创建岗位到导出首个岗位版本的完成率；
- 岗位要求有可定位证据的比例；
- 面试简报中多来源问题比例；
- 用户返回继续编辑和创建新岗位的留存。

### 9.2 质量红线

```text
无来源关键数字进入正式简历 = 0
高风险角色升级绕过审批 = 0
冻结投递快照被覆盖 = 0
未知写操作自动重放 = 0
API Key 写入源码 / SQLite / Trace = 0
MCP 或 Skill 变更后沿用旧授权 = 0
预览与正式 PDF 使用不同内容源 = 0
```

## 10. 当前实现状态

### 10.1 已实现

- 单一 Pi Agent Loop 与结构化工具调用；
- ToolGateway 权限、审批、作用域、幂等和 Trace；
- PDF 导入预览与入库前纠错；
- 岗位隔离对话与任务模型快照；
- 简历改写审批草稿恢复；
- 可解释岗位要求覆盖矩阵；
- 岗位要求的 JD 连续原文与简历 section/item 证据定位；
- 可折叠、可拖宽并持久记忆的任务上下文栏；
- 显式前端运行状态映射：连接、流式回答、工具执行、等待审批、暂停、失败和就绪；
- 流式消息按动画帧批量刷新，降低长回答期间的渲染抖动；
- 单一有效色彩 Token 源，以及浅色 / 深色 / 跟随系统和密度持久化；
- 面试情报按需加载，不阻塞主对话首屏；
- 同源编辑、预览、PDF 和独立 DOCX 导出；
- 网页搜索、网页读取、招聘页导入和受控浏览器；
- 面试知识库、面经证据和简报；
- Skill 哈希信任与 MCP 逐工具授权；
- 出站递归脱敏；
- Sidecar 重启任务对账；
- 副作用 outbox 与 `outcome_unknown`。

### 10.2 部分实现

- 任务恢复：已有重启对账，尚无完整 lease / heartbeat / atomic claim。
 - 审批草稿：已写入服务端 SQLite 审批记录并带 revision；旧 revision 保存会被拒绝。完整事件历史与 time-travel 尚未完成。
- 导入取消：客户端可停止等待，服务端解析任务仍不能协作式强制终止。
 - 证据图：已有稳定 requirement ID、JD 连续原文、简历 section/item 落点和命中片段；尚缺从证据卡到编辑器精确字符范围的高亮映射。
- 未知副作用：已有人工处置，尚无通用自动 `reconcile()`。
- MCP / Skill：已有应用层权限，尚无 OS 级沙箱。
 - Windows 打包：安装包与 packaged E2E 已通过；窗口约 1.06 秒可见、Sidecar 约 2.68 秒健康、Agent 约 2.92 秒可用。Electron/Pi Runtime 采用生产 bundle，Sidecar 排除未使用的 NumPy/OpenBLAS，只保留中英文 Chromium 语言包；安装包由 157.15 MiB 降至 122.89 MiB，减少约 21.8%。

## 11. 验收场景

使用一份同时包含教育、数据分析、产品和 Agent 项目的真实简历，创建数据分析与产品两个岗位。

必须满足：

1. 基础简历只导入一次，两个岗位共用资料库。
2. 导入错误可在入库前修正。
3. 两个岗位拥有独立对话、任务、模型快照和版本。
4. Agent 先解释岗位理解，用户可纠正。
5. 数据岗突出数据证据，产品岗突出产品证据，但均不改变事实。
6. 每条改写包含原文、JD、事实和风险。
7. 用户可接受、拒绝或编辑；失败后草稿仍在。
8. 取消任务后创建新一轮，不显示无效恢复。
9. 岗位要求矩阵展示全部要求和可定位证据。
10. 编辑器、预览和 PDF 内容一致，Word 独立可编辑。
11. 普通实时问题由通用网页工具完成，不依赖场景关键词。
12. 面试简报展示原始来源、日期、共性问题和证据充分度。
13. Skill / MCP 未授权或内容变化后不能执行。
14. 未知写操作不会自动重放。
15. 重启后旧任务不会永久停留在运行中。
16. API Key 与敏感字段不出现在任务、Trace 和模型消息中。
17. ESLint、生产构建、后端测试、前端 Runtime 测试和 packaged E2E 全部通过。
18. 切换浅色、深色和跟随系统后，重启仍保持设置，且简历文档本身不被反色。
19. 模型等待、流式回答、工具执行和审批暂停在界面上具有不同且真实的状态文案。

## 12. Definition of Done

FetchCV 当前版本只有同时满足以下条件才可进入正式发布候选：

1. 用户无需命令行即可启动。
2. 首次导入、岗位理解、改写审批、编辑导出和面试准备形成连续闭环。
3. 普通对话与业务任务共享真实 Agent Loop。
4. 所有写操作受审批、作用域、幂等和版本边界保护。
5. 简历内容受事实证据约束。
6. 基础简历、岗位版本和投递快照关系清楚。
7. 预览、编辑和 PDF 同源。
8. 关键任务可暂停、取消、恢复或明确失败。
9. 工具记录真实、可折叠、可审计且不泄露隐藏推理。
10. 自动化测试和打包后 EXE 健康检查全部通过。
11. README、PRD、客户端文案和版本一致。
12. 安装包完成 Windows 代码签名后再公开分发。
